# 로그인 계정관리 및 직책별 권한관리 작업지시서

## 1 목적과 구현 범위

공사 통합관리시스템에 로그인, 로그아웃, 계정 생성·수정·삭제, 비밀번호 변경·초기화, 직책별 권한관리를 추가한다. 계정과 권한은 별도의 어드민 계정으로 관리한다. 업무용 계정의 직책은 **대표, 팀장, 재무, 직원** 네 가지로 제한한다.

본 문서는 구현 작업지시서다. 이 문서 작성 단계에서는 애플리케이션 소스와 운영 데이터를 변경하지 않는다.

### 1.1 사용자 요구사항

- 로그인한 사용자만 업무 화면과 업무 API에 접근한다.
- 어드민이 업무 계정을 생성·수정·삭제하고 직책과 권한을 관리한다.
- 일반 사용자의 공개 회원가입은 제공하지 않는다.
- 직책을 추가하거나 삭제하는 기능은 제공하지 않는다.
- 기존 계약 → 실행예산 → 발주 → 기성 → 지급 → 준공정산 흐름과 금액 계산 규칙을 유지한다.

### 1.2 이번 구현의 설계 기준

세부 업무 권한은 아래 기본안으로 구현한다. 사용자가 지정한 네 직책과 별도 어드민 구조를 유지하면서, 변경 가능한 권한은 어드민 화면에서 조정한다.

| 항목 | 구현 기준 |
| --- | --- |
| 어드민과 직책 | 어드민은 시스템 관리용 계정 유형이며 다섯 번째 업무 직책으로 추가하지 않는다. |
| 업무 계정 | 계정마다 직책 하나만 지정한다. 개인별 예외 권한과 복수 직책은 이번 범위에 포함하지 않는다. |
| 어드민 업무 권한 | 계정·권한·관리 이력만 관리한다. 대표 결재나 실제 지급 권한을 자동 부여하지 않는다. |
| 프로젝트 접근 범위 | 첫 버전은 업무 계정이 전체 프로젝트를 조회한다. 프로젝트별 배정·열람 제한은 별도 확장 범위다. |
| 업무 기록 편집 | 직원은 본인 초안, 팀장·대표는 업무 권한이 허용된 초안을 편집한다. 기존 승인·정산완료 잠금 규칙을 함께 적용한다. |
| 계정 삭제 | 논리 삭제로 처리하고 기존 결재·작성·지급 이력과 사용자 식별자를 보존한다. |
| 인증 | Spring Security 기반 서버 세션과 세션 쿠키를 사용한다. |
| 권한 변경 반영 | 직책·권한·계정 상태 변경 후 다음 보호 API 요청부터 새 정책을 적용한다. |

전체 프로젝트 조회 범위에는 계약·원가·지급 및 프로젝트 통합현황에 포함된 손익 정보가 포함된다. 대표 대시보드 메뉴의 접근 제한만으로 개별 프로젝트 손익을 숨겼다고 간주하지 않는다.

## 3 계정과 직책 모델

### 3.1 계정 유형과 직책

| 구분 | 저장값 | 표시명 | 목적 |
| --- | --- | --- | --- |
| 계정 유형 | `ADMIN` | 어드민 | 계정·직책별 권한·관리 이력 관리 |
| 계정 유형 | `USER` | 업무 사용자 | 공사 관리 업무 수행 |
| 직책 | `CEO` | 대표 | 통합현황과 최종 결재 |
| 직책 | `TEAM_LEADER` | 팀장 | 자료 검토·작성·결재 요청 |
| 직책 | `FINANCE` | 재무 | 지급 및 정산 자료 관리 |
| 직책 | `STAFF` | 직원 | 현장·실무 자료 작성 |

- `USER`는 직책이 반드시 있어야 하고 `ADMIN`의 직책은 비워 둔다.
- 시스템 관리 권한과 업무 권한을 하나의 상하 관계로 구현하지 않는다. `ADMIN`이 `CEO` 권한을 상속해서는 안 된다.
- 일반 계정 생성 API는 `USER`만 생성한다. 요청에 `ADMIN`, 임의 권한 목록 등을 넣어 어드민으로 승격할 수 없어야 한다.
- 업무 화면 상단에는 로그인 사용자 이름과 직책, 내 비밀번호 변경, 로그아웃을 표시한다.

### 3.2 계정 입력 항목

| 필드 | 기준 |
| --- | --- |
| 로그인 ID | 영문 소문자·숫자·점·밑줄·하이픈, 4~50자. 입력은 trim·소문자 정규화 후 유일성 검증 |
| 이름 | 필수, 1~100자 |
| 직책 | 업무 계정에 필수. 네 직책 중 하나 |
| 연락처·이메일 | 선택. 이메일은 입력한 경우 형식 검증 |
| 상태 | `ACTIVE`, `INACTIVE`, `DELETED` |
| 임시 비밀번호 | 생성·초기화 시 설정. 최초 로그인 후 변경 필수 |

로그인 ID는 생성 후 변경하지 않고 삭제 후에도 재사용하지 않는다. 이름이 같아도 서로 다른 사용자 ID로 식별한다. 비활성은 복구 가능하지만 삭제는 일반 관리 화면에서 복구하지 않는다.

### 4.2 어드민의 권한 설정 범위

- 직책 네 개를 고정 탭으로 표시하고, 기능별 조회·작성·수정·요청 권한을 체크박스로 설정한다.
- 직원의 작성 권한은 항상 본인 초안 범위다. 팀장·대표의 작성 권한은 전체 초안 범위다.
- 조회 권한이 없는 기능의 작성·요청 권한은 저장할 수 없다. 권한 간 의존성을 서버와 화면에서 함께 검증한다.
- 저장 시 변경 전후 비교와 변경 사유를 받고, 해당 직책 전체 사용자에게 적용됨을 표시한다.
- 역할 생성·삭제·이름 변경, 사용자별 개별 권한 부여, 어드민의 업무 권한 부여는 제공하지 않는다.
- 기본값은 설치 시 한 번만 저장한다. 서버 재시작 시 관리자가 바꾼 권한을 기본값으로 덮어쓰지 않는다.

다음 규칙은 관리 화면에서도 변경할 수 없는 통제 규칙으로 구현한다.

1. 계정·권한관리는 `ADMIN`만 가능하다. 대표에게도 자동 부여하지 않는다.
2. 최종 승인·반려·승인취소 및 대표 전용 금액 정정은 `CEO`만 가능하다.
3. 실제 지급 등록·정정은 `FINANCE`만 가능하다. 기성 승인만으로 지급 완료를 만들 수 없다.
4. 최초 승인 금액 직접 덮어쓰기와 승인 데이터 임의 삭제를 모든 계정에서 금지한다. 기존 정정 기능도 증감·취소 이력을 보존해야 한다.
5. 승인·반려·취소, 지급, 정산완료는 기존 상태 검증을 유지한다. 권한이 있다고 업무 상태 검증을 생략하지 않는다.

잠긴 권한은 화면에 잠금 이유와 함께 표시한다. 수정 가능한 권한 키는 코드에 정의한 목록으로 제한하고, 임의 키나 잠긴 권한의 변경 요청은 서버에서 거절한다.

## 5 로그인과 비밀번호 처리

### 5.1 로그인 화면과 사용자 흐름

- PC·모바일·태블릿에서 로그인 ID, 비밀번호, 로그인 버튼을 제공한다.
- 로그인 중 중복 제출을 막고 실패 시 입력값 검증과 인증 실패 메시지를 구분한다.
- 잘못된 ID·비밀번호, 비활성·삭제·잠긴 계정은 외부에 계정 존재 여부를 드러내지 않는 공통 메시지로 처리한다.
- 정상 업무 계정은 프로젝트 목록으로, 어드민은 계정관리 화면으로 이동한다.
- 임시 비밀번호 계정은 비밀번호 변경 화면으로 이동한다. 변경 전에는 현재 사용자 조회·CSRF 발급·비밀번호 변경·로그아웃만 허용한다.
- 새로고침 시 현재 사용자 API로 로그인 상태를 복원하고 확인 전 업무자료 요청을 실행하지 않는다.
- 로그아웃·세션 만료 시 사용자·프로젝트·결재·파일 미리보기 등 메모리 상태를 비우고 로그인 화면으로 이동한다.
- 로그인 전 접근 경로를 복원할 경우 내부 경로와 현재 권한을 검증한다. 외부 URL로 리다이렉트하지 않는다.

### 5.2 인증과 세션

- Spring Security의 인증·세션 관리 기능을 사용한다. 사용자 정의 로그인 처리 시에도 세션 고정 공격 방어와 SecurityContext 저장을 빠뜨리지 않는다.
- 세션 쿠키는 HttpOnly, 운영 HTTPS에서 Secure, 기본 SameSite=Lax로 설정한다. 인증정보를 localStorage에 저장하지 않는다.
- 기본 세션 유휴 만료는 30분으로 하고 서버 설정으로 조정할 수 있게 한다. 자동 로그인은 이번 범위에서 제외한다.
- POST·PUT·PATCH·DELETE와 로그인·로그아웃에 CSRF 검증을 적용한다. 공개 로그인 API라는 이유로 CSRF를 해제하지 않는다.
- 로그인 전 CSRF 토큰을 받고 로그인 성공·로그아웃 후 새 토큰을 받는다. JSON과 multipart 모두 토큰을 헤더로 전달한다.
- 일반 접근은 인증 필요를 기본값으로 하고 로그인·CSRF·필수 정적 리소스만 명시적으로 공개한다. CORS preflight도 처리한다.
- 기존 `/api/dashboard`, 모든 `/api/v1/**`, 첨부 다운로드·미리보기를 보호한다. 알려지지 않은 API는 기본 거절한다.
- 인증 API·사용자 응답·보호된 파일 응답에 적절한 캐시 방지 정책을 적용한다.
- 개발은 기존 Vite `/api` 프록시를 우선 사용하고 운영은 같은 Origin으로 서비스한다. 직접 교차 Origin을 사용할 때만 정확한 허용 Origin과 credentials를 설정한다. 와일드카드 Origin은 사용하지 않는다.
- 운영에서는 H2 콘솔을 비활성화한다. 프록시·터널 사용 시 HTTPS와 쿠키 설정이 유지되는지 확인한다.

### 5.3 비밀번호와 잠금

- 비밀번호는 Spring Security `PasswordEncoder`와 BCrypt로 해시 저장한다. 평문·복호화 가능한 값은 저장하지 않는다.
- 이번 버전은 12~64자, BCrypt 입력 기준 UTF-8 72바이트 이내로 검증한다. 자동 자르기나 trim을 하지 않고 ID와 같은 비밀번호를 거절한다.
- 어드민이 계정 생성·초기화 시 정책을 만족하는 임시 비밀번호를 입력한다. 서버 응답과 로그에서 비밀번호를 반환하거나 출력하지 않는다.
- 비밀번호 초기화 후 기존 세션을 모두 무효화하고 최초 변경을 강제한다. 본인 변경 시 현재 비밀번호를 검증하고 변경 후 재로그인하게 한다.
- 로그인 5회 연속 실패 시 15분 잠근다. 시도 제한은 계정·요청 출처 기준으로 함께 적용하고 동시 요청으로 실패 횟수를 우회하지 못하게 한다.
- 어드민은 잠금을 해제할 수 있다. 성공한 로그인과 잠금 해제는 실패 횟수를 초기화한다.
- 별도 이메일·문자 발송이나 공개 비밀번호 찾기는 이번 범위에서 제외한다.

## 6 어드민 계정관리 기능

### 6.1 계정 목록과 편집

- 로그인 ID·이름 검색, 직책·상태 필터, 페이지 단위 목록 조회를 제공한다.
- 목록에 로그인 ID, 이름, 직책, 상태, 잠금 여부, 최근 로그인, 생성일을 표시한다.
- 신규 생성에는 로그인 ID, 이름, 직책, 임시 비밀번호, 선택 연락처를 받는다.
- 수정 화면에서는 이름, 직책, 연락처, 활성 상태를 바꿀 수 있다. 직책·상태 변경 시 사유를 받는다.
- 비밀번호 초기화, 잠금 해제, 삭제는 별도 동작과 확인창으로 제공한다.
- 삭제 확인창에는 해당 계정의 로그인이 차단되고 과거 업무 이력은 보존됨을 명시한다.
- 삭제·비활성 계정은 신규 담당자 선택 목록에서 제외한다. 과거 담당자와 작성자 표시에는 계속 나타난다.

### 6.2 변경 즉시 적용과 관리자 보호

- 사용자에 `auth_version`을 두고 비밀번호·직책·상태 변경 시 증가시킨다. 보호 API마다 DB의 최신 상태와 세션 버전을 검사한다.
- 직책별 권한을 세션에 고정 저장하지 않는다. 매 요청 시 최신 권한을 조회하거나 버전으로 검증된 캐시를 사용한다.
- 삭제·비활성·비밀번호 초기화·직책 변경 후 기존 세션은 다음 요청에서 401로 종료한다. 권한표 변경은 다음 요청에서 새 정책으로 판정하고 권한이 없으면 403을 반환한다.
- 어드민은 자기 계정 삭제·비활성 및 계정 유형 변경을 할 수 없다. 자기 비밀번호 변경은 가능하다.
- 활성 어드민이 0명이 되는 변경을 트랜잭션 안에서 방지한다. 동시 요청에서도 유지되어야 한다.
- 어드민 추가 생성은 일반 사용자 화면에서 제공하지 않는다. 필요한 경우 별도 운영 절차로 발급하며 하드코딩된 공용 비밀번호를 사용하지 않는다.

## 7 데이터 모델과 기존 데이터 전환

### 7.1 추가 테이블

실제 H2와 JPA 매핑에 맞춰 아래 모델을 추가한다. 업무 테이블과 충돌할 수 있는 예약어 `user` 대신 `app_users`를 사용한다.

| 테이블 | 주요 컬럼과 제약 |
| --- | --- |
| `app_users` | `id` 불변 PK, `login_id` UNIQUE, `password_hash`, `name`, `account_type`, `position`, `status`, `phone`, `email`, `must_change_password`, `failed_login_count`, `locked_until`, `auth_version`, `last_login_at`, `created_at/by`, `updated_at/by`, `deleted_at/by`, 낙관적 잠금용 `version` |
| `position_permissions` | `position`, `permission_key`, `allowed`, `updated_at/by`, `version`. `(position, permission_key)` UNIQUE |
| `security_audit_logs` | `id`, `actor_user_id`, 작업 당시 이름·직책 스냅샷, `action`, `target_type/id`, 정제된 `before/after`, `reason`, `result`, 서버 시각, 요청 출처·요청 식별자 |

- 계정 유형·직책·상태는 문자열 enum과 DB 제약으로 제한한다. 업무 계정 직책 필수·어드민 직책 없음 조건을 검증한다.
- 사용자 삭제 시 업무 테이블과 감사로그에 cascade delete를 적용하지 않는다.
- 시각은 서버에서 생성하고 기존 프로젝트의 시각 처리와 일관되게 저장·표시한다.
- 관리 화면의 동시 편집은 version으로 검증한다. 오래된 화면의 덮어쓰기는 409로 반환한다.

### 7.2 작성자와 승인자 연결

- 결재 요청자·승인자·취소자, 변경 작성자, 지급 처리자, 현장 기록 작성자에 불변 사용자 ID 참조와 작업 당시 이름 스냅샷을 남긴다.
- 이름 변경 후에도 과거 승인 당시 이름을 확인할 수 있어야 한다.
- 기존 문자열 작성자 컬럼은 호환성을 위해 보존한다. 새 ID 컬럼은 기존 레코드에 대해 nullable로 추가한다.
- 과거 `system`, `대표`, 자유 입력 이름을 현재 계정에 자동 귀속시키지 않는다. ID가 없는 이력은 `기존 기록`으로 표시한다.
- 소유자 불명인 기존 초안은 직원이 임의로 본인 자료로 만들 수 없다. 팀장·대표가 권한 범위에서 편집하며, 이번 구현에서는 소유권 재배정 UI를 추가하지 않는다.
- `team_leader_id`, `manager_id`는 신규·수정 입력부터 활성 업무 계정 선택으로 연결한다. 팀장은 `TEAM_LEADER`만, 담당자는 업무 계정 중에서 선택한다. 과거 자유 입력은 표시를 유지하고 명시적 재선택 전 자동 덮어쓰지 않는다.

### 7.3 초기 어드민과 설치

1. 기존 H2 데이터를 백업하고 스키마 추가·기존 데이터 보존을 검증한다.
2. 최초 어드민은 별도의 명시적 초기화 명령으로만 생성한다. ID·이름·임시 비밀번호는 환경변수 또는 비밀 설정에서 읽는다.
3. 초기화는 활성 어드민이 없는 최초 설치 상황에서만 수행하고, 재실행 시 기존 계정·비밀번호를 바꾸지 않는다. 삭제된 계정 자동 부활도 금지한다.
4. 어드민은 최초 비밀번호 변경 후 대표·팀장·재무·직원 계정을 생성한다.
5. 기존 데이터 초기화 로직이 계정·권한·감사로그나 업무 금액을 덮어쓰지 않는지 확인한다.

운영 서버의 자동 부팅 과정에서 고정된 `admin/admin` 계정을 만들지 않는다. 초기화 명령이 출력하는 값에도 비밀번호를 포함하지 않는다.

| --- | --- | --- |

| POST | `/api/v1/auth/login` | ID·비밀번호 검증, 세션 생성, 현재 사용자 응답 |
| GET | `/api/v1/auth/me` | 현재 사용자 ID·이름·계정 유형·직책·유효 권한·비밀번호 변경 필요 여부 |

| PUT | `/api/v1/auth/password` | 현재 비밀번호·새 비밀번호·확인값 검증 후 변경 및 세션 폐기 |

### 8.2 어드민 API

| Method | 경로 | 동작 |
| --- | --- | --- |
| GET | `/api/v1/admin/users` | 조건 검색·페이지 조회 |
| POST | `/api/v1/admin/users` | 업무 계정 생성 |
| GET | `/api/v1/admin/users/{userId}` | 계정 상세 조회 |
| PATCH | `/api/v1/admin/users/{userId}` | 기본정보·직책·활성 상태 변경 |

| POST | `/api/v1/admin/users/{userId}/reset-password` | 임시 비밀번호 설정 및 변경 강제 |
| POST | `/api/v1/admin/users/{userId}/unlock` | 로그인 잠금 해제 |
| GET | `/api/v1/admin/positions` | 네 직책의 권한·수정 가능 여부·의존성 조회 |

요청 필드는 명시적 DTO로 제한한다. 일반 정보 수정에서 `password_hash`, `account_type`, `auth_version`, 임의 권한을 바꿀 수 없어야 한다. 삭제 사유와 version 전달 형식은 프론트엔드와 백엔드에서 일치시키고 API 계약에 기록한다.

### 8.3 기존 API 보강

- 모든 기존 엔드포인트를 `Method + 경로 + 요구 권한 + 소유자 조건 + 대상 상태`로 목록화하고 누락 없이 권한 검사한다.
- `ApprovalRequest.request_user`, `ApprovalDecisionRequest.approver` 등 클라이언트가 보낸 행위자 이름은 제거하거나 호환 기간 동안 무시한다. 서버 Principal에서 사용자 ID·이름을 가져온다.
- `ApprovalService.decisionUser()`의 `대표` 기본값과 화면의 `system`·`대표` 하드코딩을 제거한다.
- 통합결재함은 대표에게 전체 범위, 다른 직책에는 본인 요청 범위를 서버에서 적용한다. `userId` 쿼리 조작으로 다른 사람의 결재 상세·첨부를 열 수 없어야 한다.
- 기존 `/settlement/complete`와 `/settlement/request-approval` 별칭 모두 동일한 요청 권한·상태 검증을 적용한다. 최종 완료는 대표의 승인 처리 경로에서만 발생시킨다.
- 실제 지급 API는 승인된 기성과 지급 가능 잔액을 검증하고 재무만 호출하게 한다.
- JSON·multipart 결재 요청, 첨부 다운로드, 일지 사진, 대표 전용 정정 및 변경차수 경로를 모두 점검한다. 동일 업무의 다른 URL로 권한을 우회할 수 없어야 한다.
- 파일·기성·발주·변경 등의 대상 ID가 경로의 프로젝트에 속하는지 서버에서 확인한다.
- HTTP 계층 검사와 핵심 서비스의 권한·상태 검증을 함께 적용한다. HTTP 메서드만으로 읽기·쓰기를 일괄 분류하지 않는다.

### 8.4 오류 계약

| HTTP | 의미 |
| --- | --- |
| 400 | 입력값·비밀번호 정책·직책·권한 의존성 위반 |
| 401 | 미로그인·세션 만료·인증 실패·무효화된 세션 |
| 403 | 업무 권한 부족·강제 비밀번호 변경 중 업무 접근·CSRF 검증 실패. 오류 코드로 구분 |
| 404 | 없는 대상 또는 조회 범위 밖의 개별 업무 대상 |
| 409 | 로그인 ID 중복·동시 편집 충돌·처리 불가능한 상태 변경 |
| 429 | 요청 출처 기준 로그인 시도 제한 초과 |

JSON 오류는 `code`, 사용자용 `message`, 선택적 `field_errors`, `request_id`를 사용한다. 스택트레이스·SQL·비밀번호·세션 ID는 응답하지 않는다.

## 9 프론트엔드와 백엔드 파일 구성

| 영역 | 작업 대상 |
| --- | --- |
| 백엔드 인증 | 신규 `auth` 패키지의 Controller·Service·요청/응답 DTO, 로그인 사용자 접근 컴포넌트 |
| 계정·권한 | 신규 `account` 패키지의 사용자·직책·권한 Entity/Repository/Service, 어드민 API |
| 보안 설정 | `config/SecurityConfig.java`, 기존 `CorsConfig.java`, 인증·권한 오류 처리, 사용자 상태·버전 검사 |
| 감사 이력 | 계정·권한 변경 및 로그인·결재·지급 행위의 감사 기록 컴포넌트 |
| 기존 업무 | `ApprovalService`, `ProjectController` 및 관련 변경·지급·정산·현장 서비스의 인증 사용자 연동 |
| 프론트 인증 | 신규 `features/auth`의 LoginPage·AuthProvider·PasswordChangePage·API |
| 프론트 관리 | 신규 `features/admin`의 AccountManagementPage·AccountForm·PositionPermissionPage·AuditLogPage·API |
| 공통 요청 | `lib/api-client.ts`에 인증·CSRF·오류 처리, 기존 `features/*/api.ts`의 직접 fetch와 파일 호출 전환 |
| 앱 진입 | `App.tsx`, `main.tsx`에서 로그인 확인 → 강제 비밀번호 변경 → 계정 유형별 화면 진입 순서 구성 |

현재 상태 전환 방식과 별도로 인증 경계를 구성하고 인증 상태 관리 코드를 App.tsx에 집중시키지 않는다. 새 URL 라우팅을 도입할 경우 새로고침·직접 진입도 검증한다. 권한이 없는 메뉴를 숨기면서 이벤트 핸들러에서도 실행을 차단하고 서버에서 최종 검증한다.

## 10 감사로그와 트랜잭션

- 계정 생성·수정·직책 변경·비활성·삭제·비밀번호 초기화·잠금 해제·권한표 변경을 기록한다.
- 로그인 성공·실패·잠금·로그아웃과 권한 거절도 추적한다. 비밀번호·해시·쿠키·세션 ID·CSRF 토큰과 전체 요청 본문은 기록하지 않는다.
- 변경 로그에는 실행자, 대상, 변경 전후의 허용된 필드, 사유, 결과, 서버 시각을 남긴다.
- 계정·권한 변경 성공 로그는 업무 변경과 같은 트랜잭션으로 저장한다. 실패·거절 로그는 업무 롤백으로 유실되지 않게 별도 처리한다.
- 관리 화면에서는 로그 조회만 허용한다. 수정·삭제 API는 제공하지 않는다.
- 대표 결재 및 재무 지급 이력은 계정이 삭제되어도 원래 사용자 ID와 당시 표시명을 보존한다.

## 11 작업 순서와 완료 조건

### 11.1 단계별 구현

1. **권한과 DB 기반:** 기존 API별 권한 목록, 네 직책의 권한 키·기본값·잠금 규칙, 사용자·권한·로그 모델과 데이터 전환 절차를 만든다.
2. **인증과 어드민 API:** 초기 어드민 발급, 로그인·세션·CSRF·비밀번호 처리, 계정관리와 권한관리 API를 구현한다.
3. **업무 API 연동:** 요청자·승인자 하드코딩을 제거하고 기존 조회·작성·결재·지급·파일 API 전체를 보호한다.
4. **화면:** 로그인·비밀번호 변경·계정관리·권한관리·감사로그 화면과 업무 메뉴 제어를 구현한다.
5. **통합 검증:** 기존 H2 사본에서 데이터 보존과 설치·재시작을 확인하고, 각 직책으로 업무 흐름을 검증한다.

### 11.2 필수 인수 시나리오

- [ ] 미로그인 상태에서 프로젝트·대시보드·결재·파일 API 직접 호출이 차단된다.
- [ ] 어드민 로그인 후 업무 계정 생성·수정·비활성·삭제·초기화·잠금 해제가 가능하다.
- [ ] 대표를 포함한 모든 업무 계정이 어드민 API를 호출할 수 없다.
- [ ] 어드민은 대표 승인과 실제 지급을 할 수 없다.
- [ ] 네 직책 외 입력, 복수 직책, 업무 계정의 어드민 승격, 잠긴 권한 변경이 차단된다.
- [ ] ID 대소문자·공백 정규화 후 중복이 차단되고 삭제된 ID도 재사용할 수 없다.
- [ ] 임시 비밀번호 로그인 후 변경 전 업무 API 접근이 차단된다.
- [ ] 로그인·로그아웃·JSON 저장·파일 업로드에서 CSRF 누락과 잘못된 토큰이 차단된다.
- [ ] 직원이 요청 본문에 `approver: '대표'`를 넣거나 승인 URL을 직접 호출해도 승인되지 않는다.
- [ ] 직원은 다른 사용자의 초안 수정 및 결재 요청 상세·첨부 조회를 우회할 수 없다.
- [ ] 대표의 기성 승인 후에도 지급은 미지급으로 남고 재무가 실제 지급을 별도 등록한다.
- [ ] 권한표 변경은 같은 직책 사용자 모두에게 다음 요청부터 반영되며 서버 재시작 후 유지된다.
- [ ] 삭제·비활성·직책 변경·비밀번호 초기화 후 이미 열린 다른 브라우저의 세션도 다음 요청에서 종료된다.
- [ ] 사용자명 변경·계정 삭제 후 기존 결재·지급·변경 기록과 당시 사용자명이 유지된다.
- [ ] 마지막 활성 어드민 보호와 계정·권한 동시 편집 충돌 처리가 동시 요청에서도 유지된다.
- [ ] 초기화 명령·서버 재시작으로 기존 계정·권한·비밀번호·금액이 변경되지 않는다.
- [ ] PC·모바일 로그인, 새로고침, 로그아웃 후 이전 화면 데이터 제거, 권한 없는 메뉴·버튼 처리가 동작한다.
- [ ] 기존 계약 → 예산 → 발주 → 기성 → 지급 → 정산 금액 계산과 승인 이력 보존 규칙이 유지된다.

### 11.3 검증 명령과 산출물

```powershell
cd backend
.\gradlew.bat test
cd ..\frontend
npm run build
npm run lint
```

인증·권한·소유자·세션 무효화·CSRF·대표 결재·재무 지급은 서버 통합 테스트로 검증한다. 기존 테스트도 실제 Principal 또는 명시적인 테스트 인증을 사용하도록 수정하며, 테스트 통과를 위해 운영 보안을 끄지 않는다.

완료 보고에는 변경 파일, API별 권한표, 신규 테이블·데이터 전환 결과, 초기 어드민 발급 방법, 테스트 결과, 직책별 화면 검증 결과를 포함한다. 기존 데이터와 최초 승인 금액을 보존하고 위 인수 시나리오가 통과하면 완료한다.
