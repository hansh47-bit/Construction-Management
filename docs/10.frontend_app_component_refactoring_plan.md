# 프론트엔드 `App.tsx` 기능 단위 분리 계획

## 1. 목적

현재 `frontend/src/App.tsx`에 집중된 화면 구성, 상태, API 호출, 타입, 공통 UI를 기능 단위로 분리한다.

이 작업의 목표는 공사비 흐름인 **계약 → 실행예산 → 발주 → 기성 → 지급 → 정산**을 각 기능의 코드 경계와 일치시키는 것이다. 기능 분리는 화면 표시만 나누는 작업이 아니며, 각 기능이 자신의 데이터 조회·저장·로딩·오류 처리를 관리하도록 정리한다.

## 2. 현황

`App.tsx`에는 다음 책임이 함께 있다.

- 프로젝트 목록·등록·삭제와 선택 프로젝트 상태
- 계약, 실행예산, 비교견적, 발주, 기성·지급, 정산, 결재, 변경이력 API 호출
- 화면별 편집 상태와 파일 첨부 상태
- 공통 금액·날짜 포맷 함수 및 API 주소 조합
- 각 업무 화면 패널과 공통 입력·지표 UI

화면 패널은 이미 함수 컴포넌트로 구분되어 있어 파일 이동의 기반은 있다. 다만 대부분의 데이터 조회와 저장 함수가 최상위 `App`에 있으므로, 컴포넌트 파일만 이동하면 긴 props 전달이 남는다.

## 4. 책임 경계

| 영역 | 담당 데이터와 동작 | `App`에 남길 상태 |
| --- | --- | --- |
| 프로젝트 | 목록, 검색, 등록, 삭제 | 선택 프로젝트 ID, 화면 전환 |
| 통합현황 | 계약·예산·발주·기성·지급 요약과 손익 지표 | 없음 |
| 고객 계약 | 계약 항목, 목표이익률, 계약 첨부파일 | 없음 |
| 실행예산 | 실행예산 세부 항목, 예산 결재 요청 | 없음 |
| 조달/발주 | 비교견적, 선정업체, 발주 품의, 발주 이력 | 없음 |
| 기성/지급 | 기성 등록·승인, 지급 결재 요청, 지급현황 | 없음 |
| 정산 | 준공정산 조회와 정산 완료 처리 | 없음 |
| 통합결재 | 결재 목록·상세, 승인·반려·취소 | 전역 결재 화면 여부만 필요 시 유지 |
| 변경관리 | 변경이력 조회와 변경 영향 표시 | 없음 |

`App`은 선택된 프로젝트 ID를 각 기능 화면에 전달하고, 프로젝트 미선택 상태와 상위 레이아웃만 처리한다. 업무 데이터와 저장 동작은 해당 기능 내부의 훅 또는 API 모듈이 소유한다.

## 5. 이전 순서

### 1단계: 의존성 없는 공통 코드 추출

- 금액·날짜 포맷과 `apiUrl`을 `lib`로 이동한다.
- `MoneyInput`, `Field`, `MetricPanel`, `SubMetric`을 `components/ui`로 이동한다.
- 동작 변경 없이 import 경로만 변경한다.

### 2단계: 타입과 API 모듈 분리

- 타입은 실제 공유 범위에 따라 기능별 `types.ts`에 둔다.
- 여러 기능이 함께 사용하는 프로젝트 식별 정보와 통합현황 타입만 공용 타입으로 둔다.
- 각 `fetch` 호출을 해당 기능의 `api.ts`로 이동한다.
- API 모듈은 HTTP 요청과 응답 변환만 수행하고, React 상태를 직접 보유하지 않는다.

### 3단계: 읽기 전용 화면부터 컴포넌트화

- `PurchaseOrderHistoryPanel`, `ChangeHistoryPanel`, 통합현황과 원가 추적표를 먼저 분리한다.
- 이 단계에서는 필요한 데이터와 콜백을 props로 전달해도 된다.

### 4단계: 편집 기능별 상태와 동작 이관

- 계약, 실행예산, 비교견적, 기성·지급, 정산, 결재 순서로 각 화면의 편집 상태와 저장 함수를 기능 내부로 옮긴다.
- 각 화면은 `projectId` 변경 시 자신의 데이터를 조회하고, 저장 후 자신의 데이터를 갱신한다.
- 서로 영향을 주는 저장 작업은 필요한 최소 범위에서 통합현황 갱신 콜백을 호출한다.

### 5단계: 최상위 조합 코드 정리

- `App`에서 기능별 상태와 API 함수를 제거한다.
- 선택 프로젝트, 상위 메뉴, 공통 오류 표시에 필요한 최소 상태만 남긴다.
- 중복 조회와 공용 `isLoading`·`error` 사용을 없애고 각 기능에 독립 로딩·오류 상태를 둔다.

## 6. 데이터 갱신 원칙

- 계약·실행예산·발주·기성·지급·정산의 원본 금액과 승인 이력은 백엔드가 기준이다.
- 프론트엔드는 저장 성공 뒤 해당 기능 데이터와 프로젝트 통합현황을 다시 조회한다.
- 변경 건은 계약·예산·발주에 연결되지만, 금액·승인 상태는 각 기능 API가 독립적으로 관리한다.
- 승인된 데이터는 화면에서 임의 삭제하지 않으며, 취소·정정·변경 이력 흐름을 사용한다.

## 7. 상태 관리 원칙

- 별도 전역 상태 라이브러리나 Context는 첫 분리 단계에서 도입하지 않는다.
- 선택 프로젝트 ID와 상위 화면 전환처럼 여러 기능이 실제로 공유하는 상태만 `App`에 둔다.
- 계약 항목, 예산 상세, 비교견적 편집값, 정산 입력값, 결재 반려 사유는 각 기능 컴포넌트 내부에서 관리한다.
- 여러 화면에서 같은 데이터를 동시에 갱신해야 하는 일이 반복될 때만 프로젝트 단위 Context 또는 공용 데이터 훅 도입을 검토한다.

## 8. 완료 기준

- `App.tsx`는 앱 조합과 선택 프로젝트 제어 중심의 작은 파일이 된다.
- 각 업무 영역의 타입, API 호출, 화면 컴포넌트가 같은 기능 폴더에 위치한다.
- 특정 기능의 API 오류 또는 로딩 상태가 다른 기능 화면을 덮어쓰지 않는다.
- 계약부터 정산까지 기존 API 경로와 승인 흐름이 동일하게 동작한다.
- `npm run build`가 통과한다.

## 9. 범위 제외

- 이번 구조 변경은 백엔드 API, 데이터베이스 스키마, 금액 계산 규칙을 변경하지 않는다.
- 디자인 재구성, 라우터 도입, 전역 상태 라이브러리 도입은 별도 요구가 있을 때 진행한다.
