# [작업지시서] 2단계 통합 결재함 및 실행예산/발주 결재 기능 개발

## 1. 목적

2단계 개발의 목표는 대표가 하나의 통합 결재함에서 실행예산 결재와 발주 결재를 처리할 수 있게 만드는 것이다. 1단계에서 구축된 프로젝트 중심 데이터 흐름을 유지하면서, 직원은 실행예산과 발주품의를 작성 및 결재요청하고 대표는 승인 또는 반려한다.

이번 작업의 1차 범위는 다음 두 가지로 제한한다.

- 실행예산 결재: 세부 실행예산 Roll-up 결과를 대표가 승인/반려한다.
- 발주 결재: 업체 비교견적에서 선정된 업체의 발주품의를 대표가 승인/반려하고, 승인 시 정식 발주로 확정한다.

기성/지급 결재, 변경 결재, 최종정산 결재는 같은 구조로 확장 가능하게 설계하되 이번 구현 범위에서는 제외한다.

## 2. 기존 개발 상태 요약

현재 프로젝트는 1단계 핵심 공사비 흐름의 주요 화면과 API가 어느 정도 구현되어 있다.

- 프로젝트 생성/조회 및 통합현황 API가 존재한다.
- 고객 계약/견적 입력과 목표원가한도 계산이 구현되어 있다.
- 세부 실행예산 입력, 실행항목ID별 자동 Roll-up, 목표원가한도 초과 경고가 구현되어 있다.
- 업체 비교견적 입력, 업체 단일 선정, 선정 사유 검증, 발주품의 초안 조회가 구현되어 있다.
- 발주품의 요청 API는 존재하며 `po_requisitions`에 `REQUESTED` 상태로 저장한다.
- 기성/지급 및 준공정산 기본 흐름도 일부 구현되어 있다.
- 대시보드에는 결재 관련 더미 응답이 있으나 실제 통합 결재 데이터와 연결되어 있지 않다.

현재 확인된 주요 코드 위치:

- 실행예산 상세 API: `ProjectController#getExecutionBudgetDetails`, `saveExecutionBudgetDetails`
- 실행예산 Roll-up 서비스: `ExecutionBudgetDetailService`
- 업체 비교견적 및 발주품의 요청: `VendorComparisonService`
- 발주품의 엔티티: `PoRequisition`
- 발주 확정 엔티티: `PurchaseOrder`
- 기존 결재 상태 enum: `ApprovalStatus(DRAFT, REQUESTED, APPROVED, REJECTED)`

## 3. 핵심 원칙

1. 승인 전 데이터와 승인 후 데이터는 구분한다.
2. 대표가 승인한 최초 실행예산과 최초 발주금액은 덮어쓰지 않는다.
3. 승인 이후 금액 변경은 3단계 변경관리에서 증감 이력으로 처리한다.
4. 반려된 결재 건은 삭제하지 않고 반려 상태와 반려 사유를 남긴다.
5. 결재함은 업무별 화면을 찾아가지 않아도 대표가 처리할 수 있는 단일 진입점이어야 한다.
6. 결재 승인/반려는 감사 로그의 시작점이므로 누가, 언제, 어떤 대상에 대해 처리했는지 남긴다.

## 4. 결재 상태 정의

공통 결재 상태는 기존 `ApprovalStatus`를 우선 사용한다.

| 상태 | 의미 | 수정 가능 여부 |
| --- | --- | --- |
| `DRAFT` | 직원이 작성 중 | 가능 |
| `REQUESTED` | 대표 결재 대기 | 원칙적으로 수정 불가, 수정하려면 요청 취소 또는 반려 후 재작성 |
| `APPROVED` | 대표 승인 완료 | 원본 수정 불가 |
| `REJECTED` | 대표 반려 | 반려 사유 확인 후 재요청 가능 |

MVP에서는 `CANCELED`, `CORRECTED`는 구현하지 않고 3단계 감사/변경관리에서 확장한다.

## 5. 데이터 모델 작업

### 5.1 공통 결재 테이블 추가

`approvals` 테이블을 추가한다. user가 제공한 요구사항의 통합 결재함 구조를 현재 코드에 맞게 적용한다.

```sql
CREATE TABLE approvals (
    approval_id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    approval_type TEXT NOT NULL,
    target_id TEXT NOT NULL,
    title TEXT NOT NULL,
    requested_amount DECIMAL(18, 2),
    previous_amount DECIMAL(18, 2),
    variance_amount DECIMAL(18, 2),
    request_user TEXT NOT NULL,
    request_reason TEXT,
    status TEXT NOT NULL DEFAULT 'REQUESTED',
    approver TEXT,
    comment TEXT,
    requested_at DATETIME NOT NULL,
    decided_at DATETIME,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL
);
```

`approval_type` 값:

- `EXECUTION_BUDGET`: 실행예산 최초 승인
- `PURCHASE_ORDER`: 발주 최초 승인

추후 확장 예정:

- `BUDGET_CHANGE`
- `PO_CHANGE`
- `CONTRACT_CHANGE`
- `PROGRESS`
- `PAYMENT`
- `FINAL_SETTLEMENT`

### 5.2 실행예산 승인 스냅샷

실행예산 승인 시점의 Roll-up 금액을 보존해야 한다. 현재 `project_execution_budget_items.budget_amount`는 입력 상세의 Roll-up 결과로 계속 변할 수 있으므로, 승인 금액 보존용 컬럼 또는 별도 테이블이 필요하다.

권장안: 기존 `project_execution_budget_items`에 승인 관련 컬럼을 추가한다.

```sql
ALTER TABLE project_execution_budget_items ADD COLUMN approval_status TEXT DEFAULT 'DRAFT';
ALTER TABLE project_execution_budget_items ADD COLUMN approved_budget_amount DECIMAL(18, 2);
ALTER TABLE project_execution_budget_items ADD COLUMN approved_at DATETIME;
ALTER TABLE project_execution_budget_items ADD COLUMN approval_id TEXT;
```

처리 원칙:

- 작성 중 금액: `budget_amount`
- 승인된 최초 실행예산: `approved_budget_amount`
- 승인 이후 3단계 변경관리 전까지는 `approved_budget_amount`를 변경하지 않는다.
- 통합현황의 “현재 실행예산”은 2단계 MVP에서는 승인된 실행예산을 우선 사용하고, 승인 전에는 작성 중 Roll-up 금액을 보조 표시한다.

### 5.3 발주품의 승인 보강

기존 `po_requisitions`에 승인 처리 정보를 추가한다.

```sql
ALTER TABLE po_requisitions ADD COLUMN approver TEXT;
ALTER TABLE po_requisitions ADD COLUMN comment TEXT;
ALTER TABLE po_requisitions ADD COLUMN decided_at DATETIME;
ALTER TABLE po_requisitions ADD COLUMN approval_id TEXT;
```

발주 승인 시 `purchase_orders`에 정식 발주를 생성한다.

- `po_id`: `PO-YYYY-XXX` 형식
- `project_id`: 발주품의 프로젝트
- `budget_id`: 실행항목ID
- `vendor_name`: 선정 업체명
- `initial_po_amount`: 승인된 발주금액

동일 실행항목ID에 대해 이미 승인된 발주가 있으면 중복 승인 또는 중복 발주 생성을 차단한다.

### 6.2 실행예산 결재요청 API

```http
POST /api/v1/projects/{projectId}/execution-budget-details/request-approval
```

요청 body:

```json
{
  "request_user": "system",
  "request_reason": "최초 실행예산 승인 요청"
}
```

처리 규칙:

1. 프로젝트가 정산완료 상태이면 요청 불가.
2. 세부 실행예산 상세가 1건 이상 있어야 한다.
3. Roll-up 총액이 0원이면 요청 불가.
4. 목표원가한도를 초과하더라도 요청은 가능하되 결재함에 초과 경고를 표시한다.
5. 이미 `REQUESTED` 상태의 실행예산 결재가 있으면 중복 요청 불가.
6. 이미 `APPROVED` 상태의 실행예산 최초 승인이 있으면 재요청 불가. 이후 변경은 3단계 변경관리로 처리한다.
7. `approvals`에 `EXECUTION_BUDGET` 결재 건을 생성한다.
8. 관련 실행예산 항목의 `approval_status`를 `REQUESTED`로 갱신한다.

응답은 갱신된 `ExecutionBudgetDetailResponse` 또는 생성된 `ApprovalResponse` 중 하나로 통일한다. 프론트 구현 편의를 위해 `ExecutionBudgetDetailResponse`에 `approval_id`, `approval_status`, `approved_amount`를 포함하는 것을 권장한다.

### 6.3 발주 결재요청 API 정리

기존 API를 유지한다.

```http
POST /api/v1/projects/{projectId}/purchase-orders/draft/{itemId}/request
```

기존 동작에 추가할 규칙:

1. 해당 실행항목ID의 실행예산이 먼저 승인되어 있어야 한다.
2. 선정 업체가 1개 있어야 한다.
3. 선정 사유가 있어야 한다.
4. 이미 같은 실행항목ID에 `REQUESTED` 발주품의가 있으면 중복 요청 불가.
5. 이미 같은 실행항목ID에 승인된 `purchase_orders`가 있으면 중복 요청 불가.
6. `po_requisitions` 생성과 동시에 `approvals`에 `PURCHASE_ORDER` 결재 건을 생성한다.
7. 결재함에는 승인 실행예산, 발주예정금액, 예산대비 증감액, 선정업체, 선정사유를 표시할 수 있어야 한다.

### 6.4 통합 결재함 조회 API

```http
GET /api/v1/approvals?status=REQUESTED&type=EXECUTION_BUDGET&projectId={projectId}
```

Query parameter는 모두 optional이다.

응답 예시:

```json
[
  {
    "approval_id": "APR-2026-001",
    "project_id": "prj_2026_001",
    "project_code": "P-2026-001",
    "project_name": "강남 인테리어 공사",
    "approval_type": "EXECUTION_BUDGET",
    "title": "실행예산 승인 요청",
    "target_id": "prj_2026_001",
    "requested_amount": 110000000,
    "previous_amount": 0,
    "variance_amount": 110000000,
    "request_user": "system",
    "request_reason": "최초 실행예산 승인 요청",
    "status": "REQUESTED",
    "requested_at": "2026-09-30T10:00:00"
  }
]
```

정렬:

- 기본: `requested_at DESC`
- 대표 화면에서는 `REQUESTED`가 최상단에 보여야 한다.

### 6.5 결재 상세 조회 API

```http
GET /api/v1/approvals/{approvalId}
```

타입별 상세 포함 정보:

`EXECUTION_BUDGET`:

- 프로젝트 정보
- 계약 공급가액
- 목표원가한도
- 실행예산 총합계
- 목표원가한도 초과 여부
- 실행항목ID별 Roll-up 목록
- 세부 실행예산 입력 목록

`PURCHASE_ORDER`:

- 프로젝트 정보
- 실행항목ID, 공종, 실행항목명
- 승인 실행예산
- 선정 업체
- 발주예정금액
- 예산대비 증감액
- 선정 사유
- 비교견적 목록

### 6.6 승인 API

```http
POST /api/v1/approvals/{approvalId}/approve
```

요청 body:

```json
{
  "approver": "대표",
  "comment": "승인"
}
```

`EXECUTION_BUDGET` 승인 처리:

1. approval 상태가 `REQUESTED`인지 확인한다.
2. 현재 Roll-up 금액을 승인 스냅샷으로 저장한다.
3. 각 `project_execution_budget_items.approved_budget_amount = budget_amount`로 저장한다.
4. 각 항목의 `approval_status = APPROVED`, `approved_at = now`, `approval_id = approvalId`로 갱신한다.
5. approval 상태를 `APPROVED`로 변경한다.
6. 통합현황과 업체 비교견적 화면에서 승인 실행예산 기준으로 표시되도록 한다.

`PURCHASE_ORDER` 승인 처리:

1. approval 상태와 po_requisition 상태가 `REQUESTED`인지 확인한다.
2. 실행예산 승인 여부를 다시 확인한다.
3. 동일 프로젝트/실행항목ID에 정식 발주가 이미 있는지 확인한다.
4. `purchase_orders`에 정식 발주를 생성한다.
5. `po_requisitions.approval_status = APPROVED`로 변경한다.
6. approval 상태를 `APPROVED`로 변경한다.
7. 통합현황의 현재 발주금액에 반영되도록 한다.

### 6.7 반려 API

```http
POST /api/v1/approvals/{approvalId}/reject
```

요청 body:

```json
{
  "approver": "대표",
  "comment": "견적 근거 보완 필요"
}
```

처리 규칙:

1. approval 상태가 `REQUESTED`인지 확인한다.
2. 반려 사유 `comment`는 필수다.
3. approval 상태를 `REJECTED`로 변경한다.
4. 타입별 원천 데이터 상태도 `REJECTED`로 변경한다.
5. 반려 이후 직원은 데이터를 수정한 뒤 다시 결재요청할 수 있어야 한다.

## 7. Frontend 작업지시

### 7.1 실행예산 화면

현재 `세부실행예산` 탭에 다음 기능을 추가한다.

- 결재 상태 배지: 작성중 / 결재대기 / 승인완료 / 반려
- `결재요청` 버튼
- 결재대기 또는 승인완료 상태에서는 저장/행추가/삭제 버튼 비활성화
- 반려 상태에서는 반려 사유 표시
- 목표원가한도 초과 시 결재요청은 가능하지만 경고 문구를 결재요청 전 확인하도록 표시

버튼 노출 규칙:

| 상태 | 저장 | 결재요청 | 수정 |
| --- | --- | --- | --- |
| `DRAFT` | 가능 | 가능 | 가능 |
| `REQUESTED` | 불가 | 불가 | 불가 |
| `APPROVED` | 불가 | 불가 | 불가 |
| `REJECTED` | 가능 | 가능 | 가능 |

### 7.2 업체 비교견적/발주 화면

현재 발주품의 요청 흐름에 다음 규칙과 표시를 추가한다.

- 실행예산 승인 전에는 발주품의 요청 버튼 비활성화
- 승인 실행예산 금액을 기준으로 예산대비 증감액 표시
- 발주품의 요청 후 상태를 `결재대기`로 표시
- 반려 시 반려 사유 표시 및 재요청 가능
- 승인 후에는 정식 발주번호(`PO-YYYY-XXX`)와 승인일을 표시

### 7.3 통합 결재함 화면

새 탭 또는 대표용 영역으로 `통합결재함`을 추가한다. 기존 탭 구조를 유지한다면 프로젝트 상세 탭에 추가하고, 이후 대표 대시보드로 분리할 수 있게 컴포넌트를 독립시킨다.

필수 UI:

- 상태 필터: 전체 / 결재대기 / 승인 / 반려
- 유형 필터: 전체 / 실행예산 / 발주
- 결재 목록 테이블
- 결재 상세 패널 또는 모달
- 승인 버튼
- 반려 버튼
- 반려 사유 입력

결재 목록 컬럼:

- 요청일
- 프로젝트
- 결재유형
- 제목
- 요청금액
- 예산대비 증감액
- 요청자
- 상태
- 상세보기

결재 상세에서 대표가 확인해야 할 정보:

- 실행예산: 계약금액, 목표원가한도, 실행예산 총액, 초과 여부, 실행항목별 금액
- 발주: 승인 실행예산, 선정업체, 발주예정금액, 예산대비 증감액, 선정사유, 비교견적 목록

## 8. 통합현황 반영 규칙

실행예산:

- 승인 전: 작성 중 Roll-up 금액은 실행예산 화면에서만 표시한다.
- 승인 후: 통합현황의 현재 실행예산에 반영한다.
- 승인 후 직접 수정은 막는다.

발주:

- 발주품의 요청 상태는 현재 발주금액에 반영하지 않는다.
- 발주 결재 승인 후 생성된 `purchase_orders`만 현재 발주금액에 반영한다.
- 반려된 발주품의는 현재 발주금액에 영향을 주지 않는다.

## 9. 예외 및 검증 규칙

실행예산 결재요청 차단 조건:

- 프로젝트 없음
- 세부 실행예산 없음
- 실행예산 총액 0원
- 이미 결재대기 중
- 이미 승인 완료
- 프로젝트 정산완료

발주 결재요청 차단 조건:

- 실행예산 미승인
- 선정 업체 없음
- 선정 사유 없음
- 발주예정금액 0원 이하
- 이미 결재대기 중
- 이미 승인된 발주 존재
- 프로젝트 정산완료

승인/반려 차단 조건:

- 존재하지 않는 approval
- 이미 승인/반려된 approval
- 원천 데이터가 approval과 불일치
- 반려 사유 없음

## 10. 테스트 시나리오

### 10.1 실행예산 결재

1. 프로젝트 생성
2. 고객 계약금액 입력
3. 세부 실행예산 2건 이상 입력
4. 실행항목ID별 Roll-up 확인
5. 실행예산 결재요청
6. 통합결재함에 `EXECUTION_BUDGET / REQUESTED` 표시 확인
7. 대표 승인
8. 실행예산 화면이 승인완료로 변경되는지 확인
9. 승인 후 실행예산 수정이 차단되는지 확인
10. 통합현황 현재 실행예산에 승인금액이 반영되는지 확인

### 10.2 실행예산 반려

1. 실행예산 결재요청
2. 대표 반려, 반려 사유 입력
3. 실행예산 화면에 반려 상태와 사유 표시
4. 직원이 수정 후 재요청 가능해야 함

### 10.3 발주 결재

1. 승인된 실행예산 항목 선택
2. 업체 비교견적 2건 이상 입력
3. 업체 1개 선정 및 선정 사유 입력
4. 발주품의 요청
5. 통합결재함에 `PURCHASE_ORDER / REQUESTED` 표시 확인
6. 대표 승인
7. `purchase_orders`에 정식 발주 생성 확인
8. 통합현황 현재 발주금액에 반영 확인
9. 같은 실행항목ID로 중복 발주 승인 불가 확인

### 10.4 발주 반려

1. 발주품의 요청
2. 대표 반려
3. 반려 사유 표시
4. 업체 비교견적 또는 선정 사유 수정 후 재요청 가능 확인
5. 반려 건이 현재 발주금액에 반영되지 않는지 확인

## 11. 구현 순서

1. `Approval` 엔티티, Repository, Response/Request DTO 추가
2. DB 컬럼 보강: 실행예산 승인 스냅샷, 발주품의 승인 정보
3. `ApprovalService`에 결재 목록/상세/승인/반려 공통 처리 구현
4. 실행예산 결재요청 API 구현
5. 실행예산 승인/반려 처리 구현
6. 발주품의 요청 시 `Approval` 생성하도록 기존 로직 보강
7. 발주 승인 시 `PurchaseOrder` 생성 구현
8. 통합현황 계산에서 승인된 실행예산/발주만 반영되도록 조정
9. 프론트 실행예산 탭에 결재 상태/요청 버튼/수정 잠금 구현
10. 프론트 업체 비교견적 탭에 발주 결재 상태/요청 조건 구현
11. 프론트 통합결재함 탭 또는 대표용 패널 구현
12. 테스트 데이터 및 시나리오 검증

## 12. 완료 기준

- 실행예산을 결재요청하고 통합결재함에서 승인/반려할 수 있다.
- 승인된 실행예산은 최초 승인금액으로 보존되고 직접 수정되지 않는다.
- 반려된 실행예산은 사유 확인 후 수정 및 재요청할 수 있다.
- 발주품의 요청이 통합결재함에 표시된다.
- 발주 승인 시 정식 `purchase_orders`가 생성된다.
- 반려 또는 대기 중인 발주품의는 현재 발주금액에 반영되지 않는다.
- 통합현황은 승인된 실행예산과 승인된 발주만 기준으로 계산한다.
- 승인/반려 처리 내역에는 요청자, 승인자, 사유, 처리일시가 남는다.
