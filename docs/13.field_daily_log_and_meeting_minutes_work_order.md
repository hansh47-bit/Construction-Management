# 현장 작업일지 · 현장 회의록 작업지시서

## 1. 목적과 범위

프로젝트 상세(Single View)의 중간 서브 탭에 **현장 작업일지**와 **현장 회의록**을 추가한다. 두 기능은 단순 게시판이 아니라 프로젝트별 현장 기록을 구조화해 입력·조회하는 기능이다.

- 모든 레코드는 현재 화면의 `projectId`에만 귀속한다.
- 계약·실행예산·발주·기성·지급·준공정산의 금액을 직접 변경하거나 집계에 포함하지 않는다.
- 본 문서는 구현 지시서이며, 이 문서 작성 시점에는 소스·DB·API를 변경하지 않는다.

## 2. 확정 정책 및 구현 원칙

| 항목 | 확정 정책 | 이유 |
| --- | --- | --- |
| 작업일지 1일 작성 건수 | `project_id + log_date`당 1건 | 같은 날짜의 기록이 분산되지 않고 일일 현황을 쉽게 확인할 수 있다. 정정은 수정 이력으로 남긴다. |
| 공종명 | 미리 정한 열거형이 아닌 자유 입력 + 최근 사용값 제안 | 현장별 공종이 달라 기존 고정 분류가 맞지 않는 문제를 피한다. |
| 인원 단위 | `DECIMAL(5,1)` | 반일 투입(0.5인)도 기록할 수 있다. |
| 날씨 | 날씨·기온은 우선 수기 입력 | 외부 날씨 API의 지역·시간 오차와 API 키 의존을 피한다. 자동 조회는 추후 보조 기능으로만 추가한다. |
| 회의록 상태 및 결재 | 대표 결재 없이 `DRAFT` / `SHARED` / `ARCHIVED`로 관리 | 현장 회의록은 통합결재 대상이 아니며, 작성 중과 공유 완료만 구분한다. |
| 삭제 | 작성 중인 기록만 물리 삭제, 공유된 기록은 소프트 삭제 또는 보관 | 공유된 현장 기록의 감사 추적을 보존한다. 첨부파일도 함께 정리한다. |
| 프로젝트 상태 | 공사준비·공사진행·준공·정산중에서 작성 허용, 정산완료 후 읽기 전용 | 확정된 프로젝트 이력을 보호한다. |
| 변경차수와의 관계 | 기본적으로 프로젝트 전체의 시간 이력으로 유지 | 현장 기록은 금액 변경차수에 종속시키면 과거 일지가 숨겨질 수 있다. 필요한 경우에만 선택형 `project_revision_id` 참조를 추가한다. |

작업일지는 프로젝트별·작성일자별 한 건만 생성한다. 회의록은 대표 결재를 받지 않고 공유 상태로 관리한다. 정산완료 후 예외 수정 권한은 구현 착수 전에 확정한다.

## 3. 데이터 모델

### 3.1 공통 원칙

- 날짜·시각은 서버에서 KST(`Asia/Seoul`) 기준으로 검증하고 저장한다.
- 이미지와 파일의 실제 바이너리는 DB BLOB에 넣지 않고 기존 파일 저장소에 보관한다. DB에는 저장 키, 원본명, MIME 타입, 크기만 보관한다.
- 조회·수정·파일 업로드·삭제의 모든 API는 경로의 `projectId`와 대상 레코드의 `project_id`가 일치하는지 서버에서 검증한다.
- `created_by`, `created_at`, `updated_by`, `updated_at`을 저장해 누가 언제 고쳤는지 남긴다. 공유 후 수정 시에는 수정 이력(audit log)을 남긴다.

```sql
CREATE TABLE daily_logs (
    id TEXT PRIMARY KEY,                       -- 예: DL-2026-0001
    project_id TEXT NOT NULL,
    log_date DATE NOT NULL,
    weather_condition TEXT,                    -- 맑음, 흐림, 우천 등 수기 입력
    temperature_c DECIMAL(4,1),
    site_manager_name TEXT NOT NULL,           -- 현장 책임자/작성자 표시명
    today_work_content TEXT,
    tomorrow_plan TEXT,
    safety_training_completed BOOLEAN NOT NULL DEFAULT FALSE,
    safety_training_note TEXT,
    complaint_note TEXT,
    design_change_issue_note TEXT,
    other_note TEXT,
    status TEXT NOT NULL DEFAULT 'DRAFT',      -- DRAFT, SHARED, ARCHIVED, DELETED
    created_by TEXT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by TEXT,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(project_id, log_date),
    FOREIGN KEY (project_id) REFERENCES projects(id)
);

CREATE TABLE daily_log_labor_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

CREATE TABLE daily_log_equipment_entries (

    quantity DECIMAL(12,3),

    sort_order INTEGER NOT NULL DEFAULT 0,

    sort_order INTEGER NOT NULL DEFAULT 0,
```

## 4. API 계약

### 4.1 현장 작업일지

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `GET` | `/api/v1/projects/{projectId}/daily-logs?from=&to=` | 달력 표시용 날짜별 작성 상태와 목록 조회 |
| `GET` | `/api/v1/projects/{projectId}/daily-logs/{dailyLogId}` | 선택 일자의 상세·하위 행·사진 조회 |
| `POST` | `/api/v1/projects/{projectId}/daily-logs` | 일지와 인력·장비·자재/폐기물 행을 한 트랜잭션으로 생성 |
| `PUT` | `/api/v1/projects/{projectId}/daily-logs/{dailyLogId}` | 본문 및 하위 행 전체 갱신 |
| `POST` | `/api/v1/projects/{projectId}/daily-logs/{dailyLogId}/photos` | 사진 다중 업로드 |
| `DELETE` | `/api/v1/projects/{projectId}/daily-logs/{dailyLogId}/photos/{photoId}` | 사진 제거 |
| `DELETE` | `/api/v1/projects/{projectId}/daily-logs/{dailyLogId}` | 상태와 권한에 따라 삭제/보관 |

생성·수정 요청에는 `logDate`, 기본 정보, `laborEntries`, `equipmentEntries`, `materialEntries`를 하나의 JSON으로 보낸다. 사진은 대용량이므로 별도 `multipart/form-data` API로 분리한다.

### 4.2 현장 회의록

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `GET` | `/api/v1/projects/{projectId}/meeting-minutes` | 최신 회의일시 내림차순 목록 조회 |
| `GET` | `/api/v1/projects/{projectId}/meeting-minutes/{meetingId}` | 참석자·안건·조치계획·첨부파일을 포함한 상세 조회 |
| `POST` | `/api/v1/projects/{projectId}/meeting-minutes` | 회의록과 참석자·조치계획을 한 트랜잭션으로 생성 |
| `PUT` | `/api/v1/projects/{projectId}/meeting-minutes/{meetingId}` | 상세 및 동적 하위 목록 갱신 |
| `POST` | `/api/v1/projects/{projectId}/meeting-minutes/{meetingId}/attachments` | 사진·도면·문서 업로드 |
| `DELETE` | `/api/v1/projects/{projectId}/meeting-minutes/{meetingId}/attachments/{attachmentId}` | 첨부 제거 |
| `DELETE` | `/api/v1/projects/{projectId}/meeting-minutes/{meetingId}` | 상태와 권한에 따라 삭제/보관 |

Rich Text는 클라이언트에서 작성하더라도 서버에서 허용 태그·속성만 남기도록 정제한다. 그대로 렌더링할 때도 안전한 HTML 렌더러를 사용해 XSS를 방지한다.

## 5. PC 웹 UI 설계

### 5.1 공통 탭과 주요 액션

- 기존 프로젝트 상세의 `projectTabs`에 `현장 작업일지`, `현장 회의록`을 추가한다.
- 각 탭 콘텐츠 헤더 우측 상단에 Primary Color 버튼을 고정한다.
  - 작업일지: `+ 작업일지 작성`
  - 회의록: `+ 회의록 등록`
- 같은 프로젝트의 다른 서브 탭으로 이동해도 현재 선택 날짜·열린 드로어 상태가 무분별하게 남지 않도록 탭 전환 시 상태를 정리한다.
- 최소 1280px PC 화면을 기준으로 넓은 입력 영역을 제공하고, 좁아지면 좌우 영역이 세로로 쌓이도록 한다.

### 5.2 현장 작업일지 화면

작업일지는 “좌측 미니 달력 + 우측 넓은 편집 화면”의 마스터-디테일 구조로 구성한다. 이는 사용자가 요청한 달력 기반 일일 기록 흐름에 더 적합하므로, 별도 드로어보다 우선한다.

1. 좌측(약 280~320px): 월 이동이 가능한 미니 달력, 작성됨/임시저장/공유 상태 점 또는 배지, 선택 날짜의 간단 요약을 표시한다.
2. 우측: 선택 날짜의 일지 또는 빈 상태를 표시한다. `작업일지 작성`은 선택 날짜의 넓은 편집 모달을 열고, 저장 뒤 해당 날짜 상세 화면을 갱신한다.
3. 편집 모달은 `max-width: 1280px` 수준의 넓은 중앙 모달로 하며 다음 섹션을 카드로 나눈다.
   - 기본 정보: 작성일자, 날씨, 기온, 현장 책임자
   - 출역 현황: 공종·구분·업체·투입 인원·비고를 행 추가/삭제할 수 있는 표
   - 장비 투입: 장비명·수량·비고 동적 행
   - 작업 내용: 금일 완료 상세 내역, 명일 예정 공정
   - 자재 및 폐기물: 반입/폐기물 반출 구분, 품명, 수량, 단위, 비고 동적 행
   - 특이사항: 안전교육 토글 및 상세, 민원, 설계변경 이슈, 기타
   - 현장 사진: 전/중/후 필터와 큰 썸네일 그리드, 드래그 정렬, 캡션, 개별 삭제
4. 사진은 썸네일을 먼저 표시하고 원본은 요청 시 열어, 목록 렌더링이 느려지지 않게 한다.

### 5.3 현장 회의록 화면

1. 기본 화면은 최신 회의일시 내림차순의 목록 테이블/리스트다. 회의일시, 회의명, 장소, 참석자 수, 미완료 Action Item 수, 상태를 보인다.
2. 행을 클릭하거나 `회의록 등록`을 누르면 우측에서 넓게 열리는 Drawer(권장 폭: 720px 또는 화면의 55%)를 사용한다.
3. Drawer에는 기본 정보, 소속별 참석자 동적 리스트, 안건/결정사항 Rich Text Editor, Action Items 동적 리스트, 첨부파일을 순서대로 배치한다.
4. Action Item 행은 업무·담당자·기한·상태를 포함하고, 완료 처리 시 `completed_at`을 자동 기록한다. 기한 경과 미완료 항목은 경고 색상으로 보인다.
5. 첨부파일은 사진·PDF·도면·문서를 구분 아이콘과 함께 표시하며, 파일명·크기·업로드 일시를 보여 준다.

## 6. 프론트엔드·백엔드 구현 구조

### 6.1 권장 프론트엔드 구성

```text
frontend/src/features/site-records/
  api/siteRecordsApi.ts
  types.ts
  daily-log/DailyLogPanel.tsx
  daily-log/DailyLogCalendar.tsx
  daily-log/DailyLogEditorModal.tsx
  daily-log/DailyLogPhotoGrid.tsx
  meeting-minutes/MeetingMinutesPanel.tsx
  meeting-minutes/MeetingMinutesDrawer.tsx
  meeting-minutes/ActionItemsEditor.tsx
  meeting-minutes/MeetingAttachmentList.tsx
```

- 프로젝트 상세의 탭 등록만 상위 화면에서 처리하고, 조회·저장·파일 업로드 상태는 각 기능 Panel 내부의 hook/API 계층으로 분리한다.
- 날짜·금액과 무관한 현장 기록을 기존 실행예산이나 정산 상태 객체에 억지로 넣지 않는다.
- 저장 성공·실패, 업로드 진행률, 미저장 변경사항 이탈 경고를 명확히 표시한다.

### 6.2 권장 백엔드 구성

```text
domain/site/
  DailyLog, DailyLogLaborEntry, DailyLogEquipmentEntry,
  DailyLogMaterialEntry, DailyLogPhoto
  MeetingMinutes, MeetingAttendee, MeetingActionItem, MeetingAttachment
service/
  DailyLogService, MeetingMinutesService, SiteRecordFileService
controller/
  DailyLogController, MeetingMinutesController
dto/site/
  DailyLogRequest/Response, MeetingMinutesRequest/Response 등
```

- 하위 행을 포함하는 본문 저장은 서비스 트랜잭션으로 묶는다.
- 파일 업로드 실패 시 DB 레코드만 남거나 고아 파일만 남지 않도록 저장 키 정리 보상 처리를 둔다.
- 프로젝트 삭제 기능에는 새 하위 레코드·파일 정리 범위를 추가한다. 현행 정산완료 프로젝트 삭제 제한 정책은 유지한다.

## 7. 검증 및 수용 기준

1. 서로 다른 프로젝트에서 작업일지·회의록을 생성했을 때, 다른 프로젝트 API로 ID를 조회·수정·삭제할 수 없다.
2. 작업일지는 동일 프로젝트·날짜에 중복 생성되지 않고, 기존 기록을 열어 수정할 수 있다.
3. 인력·장비·자재/폐기물·참석자·조치계획의 행 추가/삭제/정렬 결과가 재조회 후에도 동일하다.
4. 사진과 회의 첨부파일은 파일 형식·용량 제한을 검증하며, 삭제 시 저장소 파일과 DB 참조가 함께 정리된다.
5. 회의록은 최신 순으로 보이고, Drawer에서 저장 후 목록의 제목·상태·미완료 Action Item 수가 즉시 갱신된다.
6. Rich Text에 스크립트 또는 허용되지 않은 HTML을 넣어도 저장·표시 과정에서 실행되지 않는다.
7. 정산완료 프로젝트에서는 신규 작성과 수정·삭제 버튼이 비활성화되고 기록은 조회만 가능하다.
8. 기존 계약·실행예산·발주·기성·지급·정산의 금액 및 결재 집계에는 이 기능의 데이터가 포함되지 않는다.

## 8. 문제점 점검 결과

기능 방향 자체는 현재 프로젝트 중심의 단일 화면 구조와 충돌하지 않는다. 작업일지는 프로젝트별 하루 한 건으로 제한하고, 회의록은 대표 결재 없이 공유 상태로 운영하는 것으로 확정한다. 다만 아래 항목을 정하지 않으면 구현 후 데이터 정합성·보안 문제가 생길 수 있다.

1. **첨부파일 운영 기준**: 허용 확장자, 건당/건별 최대 용량, 보관 기간, 다운로드 권한이 필요하다. 특히 사진 원본을 제한 없이 허용하면 저장소와 화면 성능이 빠르게 악화된다.
2. **Rich Text 보안**: 회의 안건·결정사항에 Rich Text를 쓰려면 서버 정제와 안전 렌더링이 필수다. 단순 `dangerouslySetInnerHTML` 렌더링만으로는 안 된다.
3. **권한과 삭제**: 누가 작성·수정·공유·삭제할 수 있는지와, 공유한 회의록의 삭제 방식(보관/정정 이력)을 정해야 한다.
4. **현장 네트워크 환경**: 사진 다중 업로드는 현장에서 실패할 수 있다. 업로드 재시도·진행률·저장 전 이탈 경고를 포함해야 한다. 오프라인 임시 저장은 필요성이 확인될 때 2차 범위로 둔다.
5. **금액 흐름과 분리**: 작업일지의 설계변경 이슈나 회의 Action Item은 참고 정보다. 이를 계약·예산·발주 변경으로 자동 반영하면 승인 전 금액이 변하는 문제가 생기므로, 향후 변경관리 건을 수동으로 연결하는 방식이 적절하다.

위 정책을 확정하면, 두 기능은 기존 공사비 흐름을 훼손하지 않고 현장 운영 기록을 보완하는 구조로 안전하게 구현할 수 있다.
