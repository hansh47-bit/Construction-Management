# 작업지시서: 기성·지급 진행 후 계약 변경 연동 관리

## 1. 목적과 적용 범위

공사가 진행되어 기성 작성·승인 또는 실제 지급까지 완료된 프로젝트에서 고객 계약금액이나 계약 범위가 변경될 때, 계약 변경만 반영하고 세부 실행예산을 그대로 두는 불일치를 방지한다.

이 작업은 기존의 `CHG-YYYY-XXX` 변경 건을 중심으로 아래 금액 흐름을 연결한다.

```text
계약 변경 → 세부 실행예산 변경 → 발주 변경 → 기성 → 실제 지급 → 정산
```

이번 작업의 핵심은 **계약 변경이 등록되면 연결된 세부 실행예산 변경안을 반드시 만들고 승인 상태를 추적하는 것**이다. 발주, 기성, 지급의 이미 확정된 이력은 수정하지 않는다.

## 2. 반드시 지킬 업무 원칙

1. 최초 승인 계약금액·실행예산·발주금액, 승인 기성, 실제 지급은 직접 수정하거나 삭제하지 않는다.
2. 모든 증감은 계약 변경(`ContractChange`), 실행예산 변경(`BudgetChange`), 발주 변경(`PoChange`) 이력으로만 기록한다.
3. 계약 변경과 실행예산 변경은 같은 `change_order_id`로 연결한다.
4. 계약 증감액과 실행예산 증감액을 자동으로 같게 만들지 않는다. 계약 변경 범위와 원가 영향에 따라 공종별로 배분·검토한다.
5. 계약 변경이 승인되어도 연결 실행예산 변경이 승인되기 전에는 현재 실행예산과 현재 발주금액을 변경하지 않는다.
6. 기성 승인·실제 지급 이력은 변경 대상이 아니다. 이후 미이행 물량 및 미발주·미지급 범위에 대해서만 예산·발주 변경을 만든다.
7. 하나의 변경 건에서 계약·실행예산·발주의 승인 상태는 독립적이며, 변경 건 전체의 완료 상태는 세 단계의 처리 결과를 종합해 표현한다.

## 3. 변경 상태와 완료 기준

| 변경 건 상태 | 의미 |
| --- | --- |
| `DRAFT` | 계약 변경과 실행예산 배분안을 작성 중 |
| `REQUESTED` | 계약 또는 실행예산 변경 결재가 진행 중 |
| `PARTIALLY_APPROVED` | 계약은 승인됐지만 실행예산 또는 발주 변경이 아직 미처리·반려됨 |
| `APPROVED` | 필수 계약·실행예산 변경이 승인되고, 필요한 발주 변경도 모두 승인됨 |
| `RECONCILIATION_REQUIRED` | 이미 승인 기성·지급된 금액과 감액 변경이 충돌하여 경영진 조정이 필요한 상태 |
| `REJECTED` | 핵심 변경 결재가 반려됨 |
| `CANCELED` | 새 취소/정정 이력으로 취소됨 |

계약 변경이 발생하면 실행예산 변경안이 생성되기 전까지 변경 건은 `DRAFT`에서 결재 요청할 수 없다. 계약 변경만 승인된 경우에는 `PARTIALLY_APPROVED`로 표시하여 후속 예산 변경이 빠졌음을 프로젝트 통합현황과 변경이력에 경고한다.

## 4. 표준 업무 흐름

```text
1. 계약 변경 등록
   └─ CHG 생성, 계약 증감·사유·증빙·영향 공종 입력

2. 영향 분석
   ├─ 변경 후 계약금액 / 목표 원가한도 계산
   ├─ 세부 실행예산 변경안 자동 초안 생성
   ├─ 이미 발주·기성·지급된 금액과의 충돌 검사
   └─ 공종별 배분 금액을 담당자가 검토·수정

3. 실행예산 변경 결재 요청
   └─ 계약 변경과 같은 CHG로 통합결재함에 표시

4. 발주 영향 처리
   ├─ 미발주 항목: 변경 실행예산만 반영
   ├─ 발주 전 품의: 기존 품의 수정 또는 재작성
   └─ 승인 발주: PoChange 생성 및 별도 결재

5. 승인 반영 및 모니터링
   ├─ 각 단계 승인 시 해당 현재금액만 갱신
   ├─ CHG 타임라인과 프로젝트 통합현황 갱신
   └─ 기성·지급·정산 화면에 변경 후 잔액과 경고 표시
```

## 5. 세부 실행예산 변경안 생성 규칙

### 5.1 생성 시점

계약 변경 등록 화면에서 영향 공종을 지정하고 저장하면, 해당 `CHG`에 연결된 실행예산 변경안이 자동 생성된다. 영향 공종이 정해지지 않았으면 전체 공종에 비율 배분한 초안을 제공하되, 결재 요청 전 담당자가 공종별 증감액을 확정해야 한다.

### 5.2 배분과 검증

각 실행항목에 아래 정보를 저장·표시한다.

| 항목 | 내용 |
| --- | --- |
| 변경 전 현재 실행예산 | 기존 승인 실행예산 + 기존 승인 변경 누계 |
| 이번 증감액 | 해당 `BudgetChange`의 `+/-` 금액 |
| 변경안 금액 | 변경 전 현재 실행예산 + 이번 증감액 |
| 계약 변경 연계 | `change_order_id`, 계약 변경 금액, 사유 |
| 발주·기성·지급 현황 | 현재 발주, 승인 기성, 실제 지급, 미발주 잔액 |
| 위험 상태 | 발주초과, 기성초과, 지급완료 후 감액충돌 등 |

검증 식은 다음과 같다.

```text
변경 후 계약금액 = 현재 계약금액 + 계약 변경 증감액
변경 후 목표 원가한도 = 변경 후 계약금액 × (1 - 목표이익률)
변경 후 실행예산 = 현재 실행예산 + 승인 실행예산 변경 증감액
변경 후 발주금액 = 현재 발주금액 + 승인 발주 변경 증감액
```

실행예산 변경안은 계약 변경금액과의 단순 일치 여부가 아니라, 변경 후 목표 원가한도·공종별 견적·이미 확정된 원가를 함께 보여 주어야 한다.

## 6. 기성·지급 완료 데이터와의 충돌 처리

### 6.1 변경 불가 데이터

다음 데이터는 계약 변경 이후에도 수정·삭제하지 않는다.

- 통합결재함에서 승인 또는 반려된 기성 요청
- 실제 지급 금액, 지급일, 계좌 정보, 증빙 파일
- 지급 완료 기성의 지급 이력

오입력 정정은 기존 기록을 고치는 방식이 아니라 취소/환입/추가 지급 등의 별도 이력으로만 처리한다.

### 6.2 감액 변경의 하한선

발주 또는 실행예산을 감액할 때 아래 하한선을 검사한다.

```text
변경 후 발주금액 ≥ 승인 기성 누계
변경 후 발주금액 ≥ 실제 지급 누계
변경 후 실행예산 ≥ 이미 승인된 발주금액
```

위 조건을 만족하지 않으면 자동 승인이나 일반 결재 요청을 막고 `RECONCILIATION_REQUIRED`로 전환한다. 화면에는 초과 금액과 충돌 항목을 표시하고, 대표가 조정 사유를 기록한 별도 변경안으로만 해소할 수 있게 한다.

### 6.3 증액 변경

계약 증액 후 실행예산 증액이 필요한 경우, 실행예산 변경이 승인되기 전에는 새로운 비교견적·발주품의를 만들 수 없다. 승인 이후에만 해당 변경분을 포함한 업체 비교견적과 발주 변경이 가능하다.

## 7. 통합결재함 설계

통합결재함에는 다음 세 건을 같은 변경 ID로 묶어 표시한다.

| 결재 유형 | 제목 예시 | 승인 시 반영 |
| --- | --- | --- |
| `CONTRACT_CHANGE` | `CHG-2026-015 고객 계약 변경` | 현재 계약금액 |
| `BUDGET_CHANGE` | `CHG-2026-015 실행예산 변경` | 해당 실행항목의 현재 실행예산 |
| `PO_CHANGE` | `CHG-2026-015 발주 변경` | 해당 발주의 현재 발주금액 |

결재 상세에는 반드시 변경 전/이번 증감/변경안/승인 기성/실제 지급/충돌 여부를 함께 표시한다. 대표는 한 변경 건의 계약·예산·발주 결재 상태를 한 화면에서 확인하지만, 각 결재는 개별 승인·반려한다.

## 8. 화면 작업 범위

### 8.1 계약 관리

- `계약 변경 등록`에서 영향 공종, 증빙, 계약 증감액을 입력
- 저장 후 변경 후 계약금액, 목표 원가한도, 실행예산 변경 필요 여부를 즉시 표시
- 기성·지급 이력이 있는 프로젝트는 `기성/지급 진행 중 변경` 배지와 충돌 요약 표시

### 8.2 세부 실행예산

- `CHG`별 변경안 탭 또는 모달 제공
- 공종·실행항목별 증감 입력, 자동 배분값, 발주/기성/지급 현황 표시
- 실행예산 변경 결재 전에는 변경안 금액을 현재 예산에 반영하지 않음

### 8.3 기성 및 지급 현황

- 발주별 현재 발주금액 아래에 `변경 진행 중` 또는 `조정 필요` 상태 표시
- 이미 승인된 기성과 지급 내역은 읽기 전용으로 유지
- 감액 충돌이 있으면 기성 작성·지급요청 대신 조정 필요 사유와 변경이력 이동 버튼 표시

### 8.4 프로젝트 통합현황과 변경이력

- 계약/실행예산/발주 각각의 최초금액, 승인 변경 누계, 현재금액, 결재 대기 변경안을 구분 표시
- 변경 이력에서 계약 → 예산 → 발주 → 기성/지급 영향 순서의 타임라인 제공
- `PARTIALLY_APPROVED`, `RECONCILIATION_REQUIRED` 건은 프로젝트 경고 카드로 노출

## 9. 데이터·API 작업 범위

기존 `ChangeOrder`, `ContractChange`, `BudgetChange`, `PoChange`에 공통으로 아래 연결 정보를 보강한다.

- `change_order_id`
- 변경 전 금액, 증감액, 변경안 금액
- 결재 ID·상태·처리자·처리 시각
- 영향 실행항목/발주/기성 요약
- 충돌 상태와 조정 사유

추가 또는 확장할 API는 다음과 같다.

```http
POST /api/v1/projects/{projectId}/change-orders
POST /api/v1/projects/{projectId}/change-orders/{changeOrderId}/contract-changes
POST /api/v1/projects/{projectId}/change-orders/{changeOrderId}/budget-proposals
POST /api/v1/projects/{projectId}/change-orders/{changeOrderId}/budget-changes/request-approval
GET  /api/v1/projects/{projectId}/change-orders/{changeOrderId}/impact-summary
GET  /api/v1/projects/{projectId}/change-orders/{changeOrderId}/reconciliation
```

`impact-summary`는 계약·예산·발주·기성·지급의 변경 전/변경안/확정값 및 충돌 목록을 반환한다. 이 API를 프로젝트 통합현황, 변경이력, 통합결재함 상세에서 공통으로 사용한다.

## 10. 검증 시나리오

1. 기성·지급 이력이 없는 프로젝트에서 계약 증액 → 실행예산 변경안 → 예산 승인 → 발주 변경 순서가 정상 동작한다.
2. 지급 완료된 발주가 있는 프로젝트에서 계약 증액 시, 지급 이력은 바뀌지 않고 이후 잔액만 변경안에 반영된다.
3. 감액 후 발주금액이 승인 기성 또는 실제 지급보다 작아지는 경우 `RECONCILIATION_REQUIRED`가 되고 일반 결재 요청이 차단된다.
4. 계약 변경만 승인하고 예산 변경이 미승인인 경우 프로젝트 통합현황이 `PARTIALLY_APPROVED` 경고를 표시하며 현재 실행예산은 유지된다.
5. 실행예산 변경이 반려된 경우 계약 변경 이력은 유지되고, 새 보완 변경안 또는 취소 이력만 생성할 수 있다.
6. 하나의 `CHG` 상세에서 계약·예산·발주·기성·지급 영향 및 승인 이력을 모두 조회할 수 있다.

## 11. 완료 기준

- 계약 변경마다 연결된 세부 실행예산 변경안이 생성되고, 승인 상태가 통합결재함과 변경이력에 표시된다.
- 원본 계약·예산·발주와 승인 기성·실제 지급 데이터는 직접 수정되지 않는다.
- 계약 변경이 승인되더라도 실행예산 변경이 승인되기 전에는 현재 실행예산·발주·기성 한도가 바뀌지 않는다.
- 기성·지급 완료 데이터와 감액 변경이 충돌하면 금액을 자동으로 덮어쓰지 않고 조정 필요 상태와 근거를 제공한다.
- 프로젝트 통합현황에서 계약·예산·발주·기성·지급의 확정값과 결재 대기 변경안을 구분해 볼 수 있다.
