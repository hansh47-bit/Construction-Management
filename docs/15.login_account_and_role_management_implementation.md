# 로그인·계정·직책별 권한 구현 결과

작업 기준: `14.login_account_and_role_management_work_order.md`, 2026-10-28.

## 구현 범위

- Spring Security 서버 세션, 세션 ID 교체, HttpOnly/SameSite=Lax 쿠키, 기본 30분 유휴 만료, 로그인/로그아웃/JSON/multipart CSRF 검증을 적용했다.
- 어드민과 네 업무 직책을 분리했다. 기본표의 모순은 4.2절 변경 불가 통제 규칙을 우선하여 최종 결재·대표 정정은 CEO만, 실제 지급은 FINANCE만 허용했다. 어드민은 업무 권한을 상속하지 않는다.
- 계정 생성·검색·페이지 조회·수정·비활성·논리 삭제·잠금 해제·비밀번호 초기화, 본인 비밀번호 변경, 고정 직책 권한 편집 및 변경 전후 확인, 감사로그 조회 화면/API를 구현했다.
- 로그인 ID 정규화 및 영구 유일성, BCrypt 정책(12~64자/UTF-8 72바이트), 임시 비밀번호 강제 변경, 5회 실패/15분 계정 잠금, 요청 출처별 15분간 50회 제한을 적용했다. 알려지지 않은 계정·잠김·비활성·삭제 계정은 같은 로그인 오류를 반환한다.
- 비밀번호·직책·상태 변경은 auth_version으로 기존 세션을 다음 요청에서 종료한다. 직책 권한은 매 요청 DB에서 읽는다. 관리 수정은 version과 DB 잠금으로 동시 편집 및 마지막 활성 어드민을 보호한다.
- 모든 기존 API와 핵심 서비스에 권한을 적용했다. 직원의 초안 소유권과 결재 상세·첨부 조회 범위를 사용자 ID로 검증한다. 기존 소유자 불명 자료를 새 계정에 자동 귀속시키지 않는다.
- 새 업무 데이터에는 작성/수정 사용자 ID와 당시 이름을 기록하며, 결재에는 승인자·취소자 ID도 기록한다. 과거 문자열은 유지하고 ID 없는 이력에는 ‘기존 기록’을 표시한다.
- 지급결재 승인은 실제 지급을 생성하지 않는다. 재무가 기성별 실제 지급일·금액·증빙을 별도 등록하며, 기성 승인액 초과 및 중복 동시 지급을 막는다.
- 로그인 확인 전 업무 화면을 마운트하지 않으며, 로그아웃·세션 종료 시 업무 컴포넌트 전체를 해제한다. 인증정보를 localStorage에 저장하지 않는다. 공통 API 클라이언트가 쿠키·CSRF·401·403을 처리한다.
- 신규 프로젝트 팀장은 활성 TEAM_LEADER, 담당자는 활성 업무 계정에서 선택한다. 기존 자유 입력 담당자 값은 그대로 보존하며 신규 계정의 표시명은 삭제/비활성 후에도 조회할 수 있다.

기존 H2는 새 컬럼을 nullable로 추가하는 JPA update와 기존 schema.sql을 사용한다. 계정 논리 삭제가 업무/감사 데이터의 cascade delete를 일으키지 않는다. 샘플 데이터 자동 입력은 기본 비활성화했으며, 필요한 개발 환경만 `app.demo-data.enabled=true`로 켠다.

검증 DB 백업은 `backend/build/security-verification/source-backup.zip`에 보관했다. 사본에서 신규 인증 컬럼·테이블을 제거하여 기존 스키마 형태를 만든 후 기동했고, 업무 테이블 31개의 행 수와 전체 기존 컬럼 내용 SHA-256이 모두 동일했다. UI 검증 후에도 31개 업무 테이블은 동일했다. 별도 권한 변경 후 재시작 전후에는 계정·비밀번호 해시·변경한 권한·감사로그를 포함한 36개 테이블 모두 행 내용이 동일했다.

초기 컨텍스트 테스트에서 기본 파일 DB에 추가 인증 스키마와 기본 권한이 반영되었다. 이후 모든 자동 테스트를 전용 메모리 DB로 분리했다. 기존 업무 금액/기록은 변경하지 않았으며, 실제 작업 DB에도 어드민·업무 계정은 발급하지 않았다. 브라우저 검증 계정은 백업 사본에만 발급했다.

## 최초 어드민 발급

백엔드 중지 후 backend 디렉터리에서 실행한다. 스크립트는 기존 H2 파일을 독점 읽기로 백업한 뒤 비밀번호를 화면에 노출하지 않는 입력으로 받는다.

```powershell
cd backend
.\scripts\Initialize-Admin.ps1 -Login inc-admin -Name 시스템관리자
.\gradlew.bat bootRun
```

환경변수를 직접 설정하는 운영 절차에서는 `BOOTSTRAP_ADMIN_LOGIN`, `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_PASSWORD`를 비밀 설정으로 주입하고 `--app.bootstrap-admin=true --server.port=0`으로 실행한다. 초기화 완료 후 프로세스는 종료되며 일반 기동에서 어드민을 자동 생성하지 않는다. 계정이 하나라도 존재하면 재발급을 거절하고 기존 해시·권한·삭제 계정을 변경하지 않는다. 어드민 최초 로그인 후 비밀번호를 변경하고 네 직책의 업무 계정을 생성한다. 추가 어드민은 일반 API/화면으로 생성할 수 없다.

운영은 `prod` 프로필과 HTTPS/같은 Origin을 사용한다. `SESSION_TIMEOUT`으로 세션 유휴 시간을 조절한다. 직접 교차 Origin을 사용할 때만 정확한 `CORS_ALLOWED_ORIGINS`를 지정한다. prod 쿠키는 Secure이고 H2 콘솔은 비활성화한다. 운영 HTTPS/터널 환경 자체는 이 로컬 검증에 포함하지 않았다.

## 관리 API 계약

로그인/관리 API는 snake_case DTO를 사용한다. 계정/권한의 정의되지 않은 필드는 400으로 거절한다. 일반 업무 DTO의 기존 필드 호환성은 유지하되 클라이언트가 보낸 요청자/승인자/작성자 이름은 신뢰하지 않는다.

- GET `/api/v1/auth/csrf`: token, header_name. POST `/auth/login`: login_id, password. GET `/auth/me`: 사용자·유효 권한. POST `/auth/logout`: 세션 종료. PUT `/auth/password`: current_password, new_password, confirm_password; 성공 후 재로그인.
- GET/POST `/api/v1/admin/users`: keyword/position/status/page/size 조회 또는 USER 계정 생성. GET/PATCH `/users/{id}`: 조회/수정. PATCH는 name, position, status, phone, email, version, reason을 사용하며 직책·상태 변경에 reason이 필수다.
- DELETE `/api/v1/admin/users/{id}`: JSON `{ "version": 1, "reason": "퇴사" }`. 논리 삭제, 204.
- POST `/users/{id}/reset-password`: version, reason, temporary_password. POST `/users/{id}/unlock`: version, reason.
- GET `/api/v1/admin/positions`: 네 직책, 권한 키·표시명·허용·수정 가능·의존성·version. PUT `/positions/{position}/permissions`: permissions(변경할 키/boolean), versions(키/version), reason. 잠긴 키/알 수 없는 키/조회 의존성 위반 400, 오래된 version 409.
- GET `/api/v1/admin/audit-logs`: action/keyword/page/size. 관리 API는 ADMIN 전용이다. 페이지 크기 1~100, 0부터 시작하는 페이지 번호를 사용한다.
- GET `/api/v1/users/options`: PROJECT_READ가 있는 업무 계정 전용 활성 계정 최소 정보.
- GET `/api/v1/projects/{projectId}/access?itemId=...`: 기존 초안을 임의 소유하지 않고 현재 사용자의 계약/예산/비교견적 작성 가능 여부 조회.

오류는 code, message, request_id를 반환한다. 401은 로그인/세션, 403은 권한/강제 변경/CSRF(각 코드 구분), 404는 없는 자료/조회 범위 밖, 409는 중복/동시 편집/상태 충돌, 429는 출처별 로그인 제한이다. 보호 응답과 파일에는 no-store를 적용한다.
